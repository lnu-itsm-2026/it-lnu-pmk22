
# Runbook: Усунення ексклюзивного блокування СУБД та переповнення диска WAL

## 1. Симптоми та тригери
* Регламентне завдання обслуговування СУБД (`db-maintenance`) триває аномально довго (понад норму в 1 годину) у робочий час.
* У черзі транзакцій накопичується понад 100 заблокованих підключень (`pg_locks`).
* Диск журналів транзакцій (`pg_wal`) заповнюється зі швидкістю понад 5% за 15 хвилин або перевищує поріг 85%.
* Спостерігається каскадне зростання затримки в суміжних сервісах: таймаути запису сесій у SSO (> 10 с), уповільнення запитів Moodle та пошти (26–27 с очікування бази даних).

---

## 2. Швидка діагностика
Виконується інженером платформи (L2/L3) на сервері бази даних:

1. **Визначити PID сесії, яка наклала монопольне блокування:**
   ```sql
   SELECT pid, now() - query_start AS duration, query, state 
   FROM pg_stat_activity 
   WHERE query ILIKE '%VACUUM FULL%' AND state != 'idle';

```

2. **Оцінити кількість заблокованих транзакцій у черзі:**
```sql
SELECT count(*) AS blocked_queries 
FROM pg_locks 
WHERE NOT granted;

```


3. **Перевірити вільне місце на розділі журналів WAL:**
```bash
df -h /var/lib/postgresql/data/pg_wal

```



---

## 3. Покрокове відновлення (Workaround & Fix)

### Крок 1. Зняття монопольного блокування

Примусово скасувати блокуючий процес:

```sql
SELECT pg_cancel_backend(<PID>);

```

Якщо процес не завершився протягом 30 секунд — виконати безумовне переривання підключення:

```sql
SELECT pg_terminate_backend(<PID>);

```

### Крок 2. Звільнення дискового простору WAL

Після скасування важкої транзакції ініціювати примусову контрольну точку для скидання буферів і ротації застарілих WAL-сегментів:

```sql
CHECKPOINT;

```

Перевірити зменшення утилізації диска нижче критичного порогу 80%:

```bash
df -h /var/lib/postgresql/data/pg_wal

```

### Крок 3. Запобігання повторенню (Emergency Rollback)

1. Відкрити системний планувальник завдань (`crontab -e` або конфігурацію scheduler).
2. Скасувати щоденний запуск о 02:00 (`0 2 * * *`).
3. Перенести запуск операцій `VACUUM FULL` / `REINDEX` виключно на ніч неділі у вікно мінімального навантаження:
```cron
0 2 * * 0 /opt/scripts/db-maintenance.sh

```


4. Для повсякденної підтримки перевірити активність фонового `autovacuum` без блокування таблиць.

---

## 4. Перевірка результату

* Черга заблокованих запитів у СУБД спала до 0 (`pg_locks`).
* Використання диска журналів транзакцій впало нижче 50%.
* Час відповіді СУБД стабілізувався на рівні < 25 мс при 0% помилок підключення.
* Суміжні сервіси (SSO, Moodle, пошта) підтверджують штатний час відгуку.

---

## 5. Ескалація

* Якщо диск WAL досяг 100% і PostgreSQL перейшов в аварійний режим `read-only`, стандартний `CHECKPOINT` не спрацює.
* Негайно повідомити керівництво в коментарях інциденту: `КЕРІВНИЦТВУ: Диск WAL заповнено на 100%, потрібне погодження на аварійне розширення сховища або перезапуск сервісу СУБД`.
