# ІТ-служба ЛНУ

Це робочий репозиторій ІТ-служби Львівського національного університету імені Івана Франка.

Ви — не студенти, які виконують лабораторну. Ви — **команда ІТ-відділу**, яка тримає сервіси, від яких залежить університет. Усе, що ви робите тут, — це те саме, що робить junior у перший місяць на роботі.

## Масштаб, з яким ви працюєте

| | |
|---|---|
| Факультети, інститути, коледжі | ~20 |
| Студенти | ~20 000 |
| Викладачі та співробітники | ~3 000 |
| Корпуси й гуртожитки | 50+ |

Це означає: «перезавантажив і працює» — не рішення. Будь-яка ваша зміна може зачепити тисячі людей і сусідню команду.

## Команди й сервіси

| # | Команда | Сервіси | Залежить від | Від неї залежать |
|---|---|---|---|---|
| 1 | Пошта і файли | Email, Calendar, Drive | 2, 4, 5 | — |
| 2 | **Мережа** | VPN, Wi-Fi | 5 | усі |
| 3 | Навчання | Moodle, Service Desk, відеоконференції | 2, 4, 5 | — |
| 4 | **Ідентичність** | Сайт, SSO / LDAP | 2, 5 | 1, 3 |
| 5 | **Платформа** | БД, Backup, Monitoring | 2 | 1, 3, 4 |

Команди 2, 4, 5 — платформні: ваші зміни ламають інших. Команди 1, 3 — продуктові: ви відчуваєте наслідки чужих змін.

Граф залежностей і правила ескалації: [`docs/escalation.md`](docs/escalation.md)

## Ролі

У кожному блоці (два тижні) кожен у команді тримає одну роль. **Ролі ротуються** — за семестр ви пройдете всі.

| Роль | За що відповідає |
|---|---|
| **Service Owner** | стан сервісу і його каталог; ухвалює рішення про пріоритет |
| **Incident Manager** (чергова) | тріаж, пріоритет, ескалація |
| **Change Manager** | готує RFC, веде CAB, вирішує про відкат |
| **Risk & Knowledge** | ризики, runbooks, постмортеми |
| **Communications** | відповідь користувачу — з часом; оновлення, коли час поїхав; повідомлення про закриття |

Рольових слотів п'ять. Якщо вас п'ятеро — кожен тримає одну. Якщо четверо — хтось тримає дві. Якщо троє — двоє тримають по дві. Подвоєння теж ротується; у малих ІТ-командах так і буває.

**Communications — не «секретар».** Найчастіше служба провалюється не тому, що не полагодила, а тому, що не сказала користувачу, коли полагодить. Поки за це не відповідає конкретна людина, це нічия робота.

Хто яку роль тримає зараз — у файлі `services/<ваш-сервіс>/roles.md`. Оновлювати на початку кожного блоку.

## Як це працює щотижня

1. Викладач вкидає в цей репозиторій **події**: інциденти, запити, аварії, зміни від сусідніх команд.
2. Чергова (Incident Manager) розбирає чергу: класифікує, ставить пріоритет за [`docs/slo.md`](docs/slo.md), призначає.
3. Якщо причина не у вашому сервісі — **ескалюєте** й лишаєтесь власником комунікації. Не закриваєте тікет.
4. Зміни йдуть через Pull Request. PR, що торкається чужого сервісу, не змерджиться без рев'ю власника — це і є CAB.
5. Що дізналися — пишете в `runbooks/`. Що зламалося серйозно — у `docs/postmortems/`.

## Звідки беруться бали

Балів за «здав документ» немає. Бали — за **слід у цьому репозиторії**:

| Балів | За що |
|---|---|
| 24 | Виконання своєї ролі у 8 блоках (по 3 за блок) |
| 16 | Ваш особистий слід: створені й закриті тікети, PR, рев'ю |
| 7 | Якість командних артефактів: каталог, SLA, RCA, RFC, ризики |
| 3 | Фінальний захист: одне питання по вашій ролі |
| **50** | **разом за практичні** (решта 50 — екзамен) |

Два наслідки, які варто зрозуміти одразу:

- **Немає акаунта — немає слідів — немає балів.** Зареєструйтеся до першого заняття.
- **Час видно.** Бал за роль вимагає реакції в межах SLO, тобто в день заняття. Зробити все в останню ніч не вийде — таймстемпи в git.
- Якщо ви вважаєте бал несправедливим — покажіть тікет або PR. Це єдиний аргумент, який працює.

## Мінімальний git, якого достатньо на початку

Перші тижні вам потрібні тільки **Issues** і редагування markdown-файлу через веб-інтерфейс GitHub (кнопка з олівцем). Pull Request з'явиться в блоці 6 — до того часу навчимося.

```
# коли дійдемо до PR:
git clone <url>
git checkout -b rfc-012-mfa
# ...правки...
git add . && git commit -m "RFC-012: увімкнути MFA для співробітників"
git push -u origin rfc-012-mfa
# далі — «Create pull request» на GitHub
```

## Правила

- **Симптом окремо, гіпотеза окремо.** «Не працює пошта» — це не опис. «З 09:12 користувачі отримують SMTP 421, скарг ~40» — опис.
- **Тікет закриває той, хто його вирішив**, і тільки після повідомлення користувачу.
- **Ескалація — це не «передав і забув».** Ви лишаєтесь власником комунікації, поки користувач не отримав відповідь.
- **Персональних даних у репозиторії немає.** Репозиторій публічний. Користувачі у прикладах — «викладач кафедри X», не імена.
- **У постмортемах немає прізвищ** у розділі причин. Шукаємо причину в процесі, не в людині.
